# AGENT_GUIDE.md — read this before editing this codebase

This file exists because two real, ship-blocking bugs already happened in this project from patterns that look reasonable in isolation. Read the landmine log (§2) before touching any of the listed files. When you fix a bug or make an architectural decision, add to this file in the SAME change — it is not optional, see §3.

## 2. Landmine log (append here every time you find or fix one — do not delete old entries)

### #1 — 2026-09-26 — Per-student UI state cached by a shared key, not a composite key
**File:** `src/components/ParentPortal.tsx`. **Symptom:** two students (Aisha, Marcus) sharing the same curriculum `conceptId` ("triangle congruence tests") — clicking "View evidence" on Marcus's card displayed Aisha's cached Q&A transcript, because `replayEvents`/`replayOpenFor`/`replayLoading` were all keyed by bare `conceptId`. **Fix:** key everything by `` `${studentId}::${conceptId}` `` via a `replayKey()` helper; also clear open-panel state on student switch.
**Generalized rule:** any client-side cache or open/expanded-state keyed by a concept, lesson, or item ID that is NOT globally unique per student must be composite-keyed with the student ID. Curriculum concept IDs in this app are shared across students by design (they're curriculum, not per-student) — never assume a "concept" key alone disambiguates a student.

### #2 — 2026-09-26 — A Gemini Live tool defined but never wired to a dispatch handler is a silent no-op
**Files:** `src/live/liveConfig.ts` (tool schema definition), `server.ts` (dispatch switch), `src/adaptive/learnerStore.ts` (persistence). **Symptom:** `record_confusion_signal` was a real tool the LLM could call (and the persona prompts it to call, e.g. when a child says "I don't understand" or disagrees with the tutor) — but `server.ts`'s dispatch fell through to the generic `sendToolResponse(call, { result: 'ok' })` ack for every tool except `assess_child_reasoning`. The LLM would say "I'll make a note of that," get told "ok" by the tool response, and nothing was ever saved anywhere. **Fix:** added `recordConfusionSignal()` in `learnerStore.ts` (writes to `AffectState.confusionSignals` tally + `ConceptState.notes`) and a real dispatch case in `server.ts`.
**Generalized rule:** defining a tool in `ALL_TOOLS` (`liveConfig.ts`) is necessary but NOT sufficient for it to do anything. Every tool name must have an explicit `if (call.name === '...')` branch in `server.ts`'s dispatch switch that calls a real persistence function, or it silently falls through to the generic ack — this fails silently (the LLM thinks it worked) and is easy to miss in a demo until someone specifically checks whether the data was saved. When adding a new tool, grep `server.ts` for the tool's name to confirm a non-generic handler exists before assuming it's live.

### #3 — 2026-09-26 — One high-confidence BKT observation could mark a concept "mastered" and auto-advance the curriculum
**Files:** `src/adaptive/bkt.ts` (`EVIDENCE_QUALITY`, `updateMastery`), `src/adaptive/ladder.ts` (`computeMasteryStatus` — already correct), `src/adaptive/learnerStore.ts:367` (`cs.masteryScore = bkt.masteryScore`, unguarded), `server.ts` (two auto-advance gates). **Symptom:** demo learner Priya's "Constructing and applying properties of perpendicular and angle bisectors" concept reportedly jumped from 0% to 99% mastery after a single short exchange. Hand-verified the math: at difficulty 1, `EVIDENCE_QUALITY.transferred.guessWeight = 0.10` makes pG collapse to ~0.02 on a virgin concept, so ONE `understandingDepth: 'transferred'` observation swings the BKT posterior from a 25% prior to ~96% (`pL=0.25, pS=0.03, pG=0.02 → posterior=0.9417 → pNext=0.9592`). `computeMasteryStatus()` already correctly requires `pKnown >= 0.80 AND >= 2 distinct ladder-level-3+ items` before calling a concept even "provisional" — but `cs.masteryScore` (the raw number shown in the UI and used for curriculum auto-advance) is set directly from the BKT posterior with none of that gating. Result: the numeric mastery bar and the categorical status can disagree (bar shows 99%, status would correctly say "none"), and worse, `server.ts`'s two auto-advance checks (`/api/session/start`, `/api/session/:sessionId/assess`) compared the raw, ungated `masteryScore >= 75` directly — so a single lucky/well-classified answer could genuinely advance a child past a concept, contradicting this project's own "should not move forward simply because the child produced a correct answer" principle.
**Fix applied (complete, 2026-09-26):** two layers, both required:
1. `server.ts`: added `isConceptMastered()`, used at both auto-advance call sites — requires the properly-gated `masteryStatus !== 'none'` when that field exists (the BKT/live-voice path, where the bug lived), falling back to the raw threshold only for the legacy `recordAttempt()` quiz-click path (which never sets `masteryStatus` and was not the reported failure mode — don't "fix" it the same way without first giving it its own status computation, or you'll break advancement there).
2. `src/adaptive/learnerStore.ts`'s `recordReasoningEvidence()`: shrinks the STORED `cs.masteryScore`/`cs.pKnown` to `MASTERY_THRESHOLD - 1` whenever `cs.masteryStatus === 'none'` but the raw posterior implied "mastered" — fixed AT THE SOURCE, not just at the advance gate or in the UI, because the raw ungated number also fed the tutor's own `/api/learner-context/*` prompt text and `src/plan/compile.ts`'s prerequisite-strength check (`pKnown < 0.6`), both of which could have let the tutor itself believe a child had mastered something from one answer. All downstream consumers (event log, `EvidenceEvent`, the live WS update, API responses, UI) now read this same one final number. See `docs/LEARNER_MODEL.md §6.1` for the full BKT-level explanation and why `EVIDENCE_QUALITY`'s guess/slip weights were deliberately left untouched (recalibrating them would be arbitrary tuning with no principled basis; reusing the existing evidence-sufficiency rule from `computeMasteryStatus` is not).
**Verified, not just asserted:** wrote and ran a standalone repro script bundling the real `learnerStore.ts` against a temp data dir — confirmed (a) one `transferred` observation on a virgin concept now stores 74%/`'none'` instead of 96%, and (b) two more genuine, distinct-item `transferred` observations still correctly climb the score and flip status to `'provisional'` — so legitimate multi-observation progression was not broken by the fix. `npx tsc --noEmit` clean; `npm run test:assessor` (unaffected code path) still passes; `npm run test:live` fails identically on the ORIGINAL unmodified code in this environment (confirmed via `git stash`) — a pre-existing sandbox/network limitation (no reachable Gemini Live endpoint here), not a regression.
**Generalized rule:** whenever a system computes two different signals that both claim to represent "how well does this learner know X" (a continuous score AND a categorical status), fix disagreements AT THE SOURCE that computes the continuous one, not by gating each consumer separately — there will always be another consumer (a prompt, a new UI, an API route) you didn't think to gate. Reuse an existing, already-validated evidence-sufficiency rule before inventing a new tunable constant.

## 3. The doc-sync rule (how this stays honest)

Every commit that touches a file in the left column of §1's table should touch the doc(s) in the corresponding right column in the SAME commit — not "later." This is enforced (as a warning, not a hard block, given hackathon time pressure) by `scripts/check-docs-sync.mjs`, wired to `npm run check:docs` and to a pre-commit hook at `.githooks/pre-commit` (enabled via `git config core.hooksPath .githooks`, already set in this repo — see `docs/ARCHITECTURE.md`). If the hook warns you and you deliberately want to skip updating docs (e.g. a pure typo fix), that's fine — it's advisory, not blocking — but a **new landmine, a new architectural decision, or a change to what a tool/route/persona does** should never be skipped.

If you are an AI agent and you just fixed a bug or changed a design decision: add a landmine entry (§2) or a `DECISIONS.md` entry BEFORE you consider the task done. This file existing and being stale is worse than it not existing.
